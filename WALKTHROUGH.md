# Demo Walkthrough Script (3–5 minutes)

Expected numbers below are from a verified run of the current sample data —
the mock pipeline is deterministic, so you should see the same values.

## 0:00 — Framing (20s)

> "This is a retail data workbench: upload CSVs, clean them with a full audit
> trail, and ask questions in plain English. Every answer is grounded — the
> prose is generated by string templates over computed numbers, and the raw
> evidence is one click away."

## 0:20 — Upload → Profile → Clean (30s)

Upload the 5 sample CSVs, click Profile, then Clean.

**Point at:** the before→after table — customers 80→76, stores 10→9, orders
300→297, products 60→60 with `Electronic` merged into `Electronics`. "Cleaning
is deterministic code, and it's honest about what it *didn't* do: the
`skipped` column is a high-risk duplicate-ID step that is flagged for manual
review instead of silently dropping rows. The category merge is mechanical —
it even says in the step reason that synonyms are NOT merged."

## 0:50 — Analytics (30s)

Click View Analytics.

**Point at:** revenue by category, stockout list. "Same analytics functions
the chat uses — no separate implementation to drift out of sync."

## 1:20 — Chat: grounded answer + evidence (60s)

Start Chat Session, ask: **"What is the revenue by category?"**

- Green **ok** badge; answer names Electronics, 11414.66, AOV 184.11.
- Expand **Evidence**: `plan.capability = "revenue_by_category"`,
  `computed_from` shows 297 orders and 10 excluded negative/null-revenue rows.

> "The LLM never writes this answer. A code router matched this question to a
> real analytics function; the text is a template over its output. Expand the
> evidence and you can recompute every number."

Follow up: **"Which categories had the highest return rate among those?"**

- Home & Office 3.3% (1 of 30). "Note the assumption shown in the evidence:
  a 'return' is an order with negative revenue — a data-model decision made
  in code and disclosed in every answer."

## 2:30 — Multi-turn context carry (50s)

Ask: **"Show me orders in the West region"** → 146 of 297 orders, 24239.18.

Then repeat: **"Which categories had the highest return rate among those?"**

- Evidence now shows `region_filter_applied: true`, computed from **146** West
  orders only — Footwear 6.2% (1 of 16).

> "The second question never mentions West. The session carried the filter
> forward — and it applies to the analytics path too, not just generic plans."

## 3:20 — Safety behaviour (40s)

Ask: **"compare"** → yellow `clarification_needed`.
Ask: **"What will our competitor's prices be next year?"** → red `refused`.

> "Out-of-scope and vague questions are refused or clarified — never guessed
> at. These are modelled outcomes with their own persisted turns."

## 4:00 — Defense-in-depth & evaluator (45s)

> "Underneath this: any plan — human-typed or LLM-generated — passes the same
> allow-list validator; a hostile `limit: 999999` plan is rejected in tests.
> Poisoned cell text flows through as inert data, byte for byte, and is never
> interpreted. 101 tests cover this, including a batch evaluator that runs the
> whole pipeline headlessly — edge cases like a 100k-row file, an all-null
> column and a latin-1 encoding, plus one deliberately broken case, and the
> other eight still pass."

## 4:45 — Close (15s)

> "In one line: deterministic data work, an LLM that can only *suggest*,
> validation as the security boundary, and evidence for every number."
